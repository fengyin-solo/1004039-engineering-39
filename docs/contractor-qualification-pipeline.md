# 施工队伍资质链路与构建前校验

施工队伍（contractor）模块的资质样例与构建校验以前靠人工对照：新增资质类型时容易漏改校验
条件，构建虽然通过，页面上却可能出现无法安排作业的队伍。本文把**资质链路**和**样例准备 →
构建前校验**流程固定下来，规则只有一个来源，新增类型只改一处。

## 一、资质完整链路

### 1. 作业状态链

```text
待审核 ──审核备案──▶ 已备案 ──安排作业──▶ 作业中
  │                   │                   │
  └───────────────────┴──── 清退队伍 ────┴──▶ 已清退（终态）
```

- 只有 `待审核` 能审核备案；只有 `已备案` 能安排作业。
- `作业中` 不能直接清退，需先完工退回 `已备案` 再清退；`已清退` 是终态。

### 2. 资质链路的四道条件（顺序即排查顺序）

| 顺序 | 条件 | 规则 |
| --- | --- | --- |
| ① 所属企业 | 企业必须在备案企业名录内 | `REGISTERED_ENTERPRISES` |
| ② 资质等级 | 市政公用工程总承包 `特级 > 一级 > 二级 > 三级`，作业门槛 **二级及以上** | `QUALIFICATION_LEVELS` / `MIN_ASSIGN_QUALIFICATION` |
| ③ 特种作业证 | 同时持有「地下有限空间作业操作证」「焊接与热切割作业证」 | `REQUIRED_SPECIAL_CERTS` |
| ④ 作业状态 | 状态链上的动作流转合法 | `CONTRACTOR_ACTIONS` |

### 3. 不同类别队伍适用的校验

| 队伍类别 | 结构校验 | 完整资质链路（①②③） |
| --- | --- | --- |
| 待审核队伍 | ✅ | 豁免（资质尚在审核，备案时才把关） |
| 已备案队伍 | ✅ | **必须满足**，否则页面无队可派 |
| 作业中队伍 | ✅ | **必须持续满足** |
| 已清退队伍 | ✅ | 豁免（已退出作业市场，特种作业证字段允许为空） |

另设一条**全局门禁**：至少存在 1 支满足完整链路的 `已备案` 队伍，否则直接判失败
（页面上将无法安排作业）。

> 关键设计：审核备案与安排作业共用同一套链路门禁。备案通过即代表可以派活，从根上避免
> “已备案却安排不了作业”。

## 二、规则唯一来源

`frontend/src/data/contractor/domain.ts` 是唯一规则源：

- 运行时动作门禁：`src/api/local-service.ts` 调 `contractorTransition()`；
- 构建前校验：`scripts/contractor/validate.mjs` 通过 esbuild 加载同一份 TS 源；
- 标准样例目录：`src/data/contractor/catalog.json`。

新增资质等级 / 特种作业证 / 备案企业时，**只改 `domain.ts`（和需要时的 catalog.json）**，
运行时门禁与构建校验自动同步，不会再两处各改一遍、漏掉一处。
`modules.ts` 里 contractor 的状态/动作/字段会与规则源交叉核对，不一致就构建失败。

## 三、流水线：样例准备 → 构建前校验

入口在 `frontend/scripts/contractor/`：

| 命令 | 作用 |
| --- | --- |
| `npm run contractor:prepare` | 阶段 1：把标准目录合入 `src/data/seed.ts` |
| `npm run contractor:validate` | 阶段 2：按完整链路校验 seed |
| `npm run contractor:pipeline` | 顺序执行两阶段（默认跳过输入未变的已通过阶段） |
| `npm run build` | `prebuild` 钩子自动先跑流水线，失败则构建中止 |

流水线参数：

- `--force`：忽略状态文件，两阶段全部重跑；
- `--stage prepare` / `--stage validate`：只重跑指定阶段（**修复后单独重跑失败环节**）。

### 阶段 1：样例准备（prepare）的合入规则

按**队伍编号**把 `catalog.json` 合入 seed 的 contractor 数组，天然按编号去重：

- `已备案` / `作业中` 队伍：仍满足完整链路的**原样保留**（已有备案队伍、作业中队伍不受影响）；
  不再满足的（如企业被移出名录）用标准目录修复；
- `待审核` / `已清退` 一律以目录为准；
- 目录之外的额外队伍原样保留，是否合法交给阶段 2；
- 结果稳定、无内容变更时不写文件，**重复执行不产生重复样例、无多余 diff**。

### 阶段 2：构建前校验（validate）

0. 规则交叉核对：`modules.ts` 的状态/动作/字段与 `domain.ts` 一致；
1. 结构：id 与队伍编号唯一、字段完整、状态合法、字段「队伍状态」与当前状态一致；
2. 分类门禁：已备案/作业中必须满足完整链路，待审核/已清退只过结构；
3. 全局门禁：至少 1 支可派活的已备案队伍。

失败按「**哪类队伍 + 哪项条件**」报出，例如：

```text
✗ 已备案队伍 CONT-0002（恒泰管网综合施工队，当前状态「已备案」）：资质等级不足
   —— 资质等级为三级，安排作业要求二级及以上
✗ 作业中队伍 CONT-0003（…）：企业未备案 —— 所属企业「某挂靠工程队」不在备案企业名录内
✗ 全局门禁：没有任何一支满足完整资质链路的已备案队伍，页面上将无法安排作业
```

### 增量与重跑

阶段结果与各阶段**输入文件指纹**（seed / catalog / domain / modules）记在
`frontend/.contractor-pipeline-state.json`（已 gitignore）：

- 上次通过且输入指纹未变 → 跳过；任一输入被改动 → 自动重跑，旧结果不会放行新数据；
- 失败后只修对应文件，执行 `npm run contractor:pipeline -- --stage <阶段>` 单独重跑。

## 四、典型操作

```bash
cd frontend

# 新增/调整资质规则后：改 domain.ts，然后全量重跑
npm run contractor:pipeline -- --force

# 校验失败、修完 seed 或目录后：只重跑失败环节
npm run contractor:pipeline -- --stage validate

# 正常构建（自动先跑流水线）
npm run build
```
